# Project Rules

1. Use schematic terminology only. Refer only to physically probeable points/components (for example: C2 N2A leg, R2 N1A leg, MCP6022 pin 3). Do not use wire/net names alone as probe instructions, and do not identify components by values unless explicitly asked.

2. Use GitHub-compatible math formatting in Markdown files. Inline math must use `$...$`. Display math must use `$$` on its own lines, with a blank line before the opening delimiter and after the closing delimiter. Do not use `\(...\)`, `\[...\]`, or bare `[ ... ]` as math delimiters. Write units inside math with LaTeX-safe formatting such as `40\,\mu\text{s}`, `1\,\text{kHz}`, and `25\,\text{kSa/s}`. To avoid the GitHub math-parser errors observed in this repository, do not place percentage signs inside display-math expressions; write the decimal value in the formula and state the percentage in surrounding prose. Before committing a Markdown file containing formulas, verify that all math delimiters and braces are balanced and that no LaTeX command is left outside a math block.

3. Use clear, simple English in all project answers and documentation. Prefer common, everyday words and short, direct sentences. Avoid rare words, jargon, and unnecessarily complex phrases when simpler wording has the same meaning. Keep necessary engineering terms, but explain each new or difficult term in plain language when it first appears. Explain technical ideas step by step without losing important details or accuracy. For example, say "regular timing between samples" instead of "sampling cadence".

4. Be concise and informative. Include only information that helps answer the question, understand the concept, or carry out the next step. Avoid filler, repeated warnings, routine disclaimers, generic introductions, needless summaries, and status notes. Do not repeatedly state that study examples are hypothetical when the context already makes that clear. Explain assumptions or uncertainty only when they matter for correctness, safety, or a decision. Give enough technical detail when the user asks for it, but do not add unnecessary text. Write naturally, not like a template.
